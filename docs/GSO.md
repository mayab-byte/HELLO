# GSO ונגישות — מה שנאכף בכל אתר

SEO קלאסי נלחם על מיקום בעמוד תוצאות. **GSO** (Generative Search
Optimization) נלחם על משהו אחר: שהמודל שעונה לגולש יצטט **אותנו**.

מודל לא מדרג קישורים, הוא בונה תשובה. כדי להיכנס לתשובה הזו הוא צריך
שלושה דברים שאתר רגיל לא טורח לתת לו:

| מה המודל צריך | איפה זה בתשתית |
|---|---|
| ישות מוגדרת — מי העסק, במונחים שמכונה מבינה | `siteGraph()` ב-`lib/gso.ts` |
| תשובות מפורשות — שאלה ותשובה, גלויות **וגם** מסומנות | `dna.gso.answers` → `components/site/Faq.tsx` |
| מפה קריאה — מה יש באתר ולמי הוא מיועד | `/llms.txt` |

הכל נגזר מבלוק אחד ב-`dna.ts`, ונאכף ב-`scripts/check-gso.mjs`.

---

## למה אכיפה ולא המלצה

תשתית תבנית היא הבטחה, לא ערובה. אפשר לכתוב את הכלים הכי טובים לגזירת
`schema.org` ולייצור `llms.txt`, ומי שישכפל את המאגר עדיין ישאיר את
הפלייסהולדרים, ימחק את סקשן השאלות, יוסיף עמוד בלי `canonical`, או יוריד
את תפריט הנגישות "כי הוא מפריע לעיצוב".

לכן הבדיקה עובדת בדיוק כמו `check-dna.mjs`: **אתר שלא עומד בעקרונות לא
נבנה.**

### שני מצבים

| מצב | מתי | מה קורה |
|---|---|---|
| **תבנית** | `dna.meta.client` עדיין `'אתר דוגמה'` | אזהרות, הבנייה עוברת |
| **לקוח** | `client` הוחלף בשם אמיתי | כשלים, הבנייה נופלת |

כך המאגר-אב נבנה כמו שהוא, והשער נסגר ברגע שמישהו הופך אותו לאתר לקוח.

```bash
npm run check:gso          # הרצה ידנית
GSO_STRICT=1 npm run check:gso   # כפיית מצב לקוח, גם על התבנית
GSO_STRICT=0 npm run build       # פתח חירום. לא דרך עבודה.
```

## מה נבדק

### ישות

- `seo.siteUrl` הוא `https` ואינו כתובת דוגמה
- `seo.description` באורך 70 עד 160 תווים
- `gso.entity.type` חוקי, ו-`LocalBusiness` מחייב `geo` תקין
- `identity.legalName` · `phone` · `email` · `address` אינם פלייסהולדרים
- לפחות פרופיל חיצוני אחד ב-`sameAs` (או ב-`identity.social`)
- `gso.hours` בפורמט `HH:MM` עם קודי יום חוקיים

### תשובות

- לפחות **5** שאלות ותשובות
- כל שאלה מסתיימת בסימן שאלה ובאורך 10 תווים לפחות
- כל תשובה באורך **120 תווים לפחות** — תשובה בת שורה אחת לא נותנת למודל
  מה לצטט. מספרים, טווחים ותנאים הם מה שנבחר בפועל
- אין שאלות כפולות
- הסקשן `faq` פעיל

### llms.txt

- `gso.llms.summary` באורך 40 תווים לפחות
- לפחות שני נושאים ב-`gso.llms.topics`
- `gso.crawlers` הוא `allow` או `block`

### נגישות

- שלושת המסמכים קיימים כקבצים: `/accessibility` · `/privacy` · `/terms`
- שלושתם מקושרים ב-`dna.legalLinks`
- `<AccessibilityMenu />` מורכב ב-`app/(site)/layout.tsx`
- פרטי רכז הנגישות אינם פלייסהולדרים
- `accessibility.level` הוא `AA` לפחות

### מבנה האתר

זו הבדיקה שמחזיקה גם באתר שעוד לא נכתב. כל שאר הכללים בודקים ערכים
שאנחנו מכירים; כאן נסרק עץ הקבצים בפועל, ולכן עמוד שמישהו יוסיף בעוד שנה
לאתר שאיננו מכירים ייתפס באותה מידה.

- כל `app/(site)/**/page.tsx` מייצא `metadata` או `generateMetadata`
- כל אחד מהם עובר דרך `pageMeta()` — כלומר מקבל `canonical`
- `app/layout.tsx` מזריק את `siteGraph()`
- `<Faq />` מוצג בעמוד הבית
- `app/llms.txt/route.ts` קיים כל עוד `gso.llms.enabled` פעיל

## העיקרון שמחזיק את הכל

**הסימון נגזר מאותו מקור שמזין את המסך.**

`components/site/Faq.tsx` מציג את השאלות **וגם** פולט את ה-`FAQPage`,
משניהם מ-`dna.gso.answers`. `components/site/PageHeader.tsx` מצייר את
פירורי הלחם **וגם** פולט את ה-`BreadcrumbList`, משניהם מאותו מערך
`crumbs`.

זו לא נוחות. סימון תוכן שאינו גלוי בעמוד הוא הפרה מפורשת של הנחיות גוגל,
וכאן פשוט אין דרך להגיע למצב הזה — הסימון והמסך לא יכולים להיפרד.

התוצאה המעשית: מפתח שמוסיף עמוד פנימי חדש ומשתמש ב-`PageHeader` מקבל
היררכיה סמנטית בלי לדעת שהיא קיימת.

## מה מיוצר בפועל

| כתובת | מה יש שם |
|---|---|
| כל עמוד | `Organization`/`LocalBusiness` + `WebSite`, מקושרים ב-`@id` |
| כל עמוד | `canonical` מפורש |
| עמוד פנימי | `BreadcrumbList` |
| `/` · `/faq` | `FAQPage` |
| `/blog/[slug]` | `Article` עם מחבר, מפרסם, `mainEntityOfPage` ותאריכים |
| `/services/[id]` | `Service` מקושר לספק |
| `/llms.txt` | הישות, הנושאים, כל התשובות, השירותים, המאמרים והעמודים |
| `/robots.txt` | רישום מפורש של עשרה סורקי AI |
| `/sitemap.xml` | כולל `/faq` בעדיפות 0.8 |

### סורקי ה-AI ב-robots.txt

`GPTBot` · `OAI-SearchBot` · `ChatGPT-User` · `ClaudeBot` ·
`anthropic-ai` · `PerplexityBot` · `Google-Extended` ·
`Applebot-Extended` · `CCBot` · `Bytespider`

הכלל הגורף כבר מרשה להם מכללא, אבל "מכללא" אינה החלטה. הרישום המפורש
הופך את זה לבחירה של הלקוח בשדה אחד — `dna.gso.crawlers`.

## תפריט הנגישות

חובה חוקית בישראל, ולכן מוטמע ב-`app/(site)/layout.tsx` ואינו ניתן
לכיבוי דרך `dna.sections`.

**מה הוא מציע:** גודל טקסט 100% עד 160%, ניגודיות גבוהה, מצב כהה, הדגשת
קישורים, גופן קריא, הגדלת ריווח, עצירת אנימציות, סמן גדול, סרגל קריאה,
ביטול כל ההתאמות, וקישור להצהרה המלאה.

שלוש החלטות מימוש שכדאי להכיר:

1. **ההעדפות נטענות לפני הצביעה הראשונה.** סקריפט קצר ב-`<head>` קורא
   מ-`localStorage` ומחיל את המחלקות. בלעדיו מי שבחר ניגודיות גבוהה רואה
   הבזק של העמוד הרגיל בכל טעינה — כלומר דווקא המשתמש שהכי תלוי בהתאמה
   הוא זה שרואה אותה נשברת.

2. **כל ההתאמות הן CSS על `<html>`.** אין נגיעה ב-DOM של התוכן, ולכן שום
   התאמה לא יכולה לשבור פריסה של אתר לקוח שאיננו מכירים מראש.

3. **הצבעים של התפריט קבועים ואינם נגזרים מפלטת המותג.** זו הנקודה:
   כשלקוח מחליף פלטה, תפריט הנגישות חייב להישאר קריא בלי תלות בבחירה
   שלו. הניגודיות שם היא 15.9:1.

## מה עושים בשכפול ללקוח חדש

1. למלא את `gso.entity` — סוג, שנת הקמה, טווח מחירים, אזורי שירות, `geo`
2. למלא כתובות מלאות ב-`identity.social` (לא `'#'`)
3. למלא את `gso.hours` בפורמט קריא-מכונה
4. **לכתוב מחדש את `gso.answers`.** זה החלק שדורש עבודה אמיתית ולא
   העתקה. השאלות צריכות להיות מה שגולש באמת שואל, והתשובות צריכות להכיל
   מספרים וטווחים. זה מה שנבחר לציטוט
5. לעדכן את `gso.author` ואת `gso.llms`
6. למלא את פרטי רכז הנגישות
7. להריץ `npm run check:gso` עד שהוא נקי
